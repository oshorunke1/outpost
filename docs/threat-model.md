# Threat model v1: client exploits

Scope for M1: a malicious or modified Roblox client attacking the game server. The attacker controls everything on their own machine, can fire any RemoteEvent that exists with any arguments at any rate, and can teleport their own character. They cannot run code on the server. Backend, credential and agent threats are planned (M2) and planned (M3), in v2 of this document.

The design is described in [ARCHITECTURE.md](../ARCHITECTURE.md). Every row below names the code that does the defending and the test or check that proves it. Where a defence has no automated proof, the row says so.

## Known gaps

These are real limitations in the M1 code, listed so nobody has to find them the hard way.

- **A yielding Init's thread is not closed.** `Loader.InitAll` warns about an Init that yields and never Starts that module, but it does not call `coroutine.close` on the suspended coroutine. If whatever it waited on resumes it, the rest of that Init runs late, after `Seal`. A `NetGuard.Listen` at that point errors because the gate is sealed, but any other side effect of that Init would still happen. See `game/src/ReplicatedStorage/Shared/Util/Loader.luau`.
- **`NextOrbId` has no wrap.** Orb ids count up forever on each server, but the `Orb.Collect` payload spec caps `OrbId` at 1,000,000. After a million orb spawns on one server, new orbs can no longer be collected (every request is `BadPayload`). At the sustained limit of about 4 pickups a second that takes roughly 69 hours of nonstop collecting on one server. See `game/src/ServerStorage/Classes/Services/OrbService.luau`.
- **Outbound payloads are not checked at runtime.** Server-to-client packets have payload specs (for example `Profile.Snapshot` caps Coins at 1,000,000,000), but `NetGuard.SendTo` only checks the direction, not the payload. Those specs document the shape for the client and the manifest.
- **`GetData` returns the live save table.** Code that writes to it directly skips the check in `Update`. The release check (`PlayerRemoving` and `BindToClose`) protects the final save, but ProfileService autosaves every loaded profile on a 30 s cycle (`AutoSaveProfiles = 30` in `game/vendor/ProfileService.luau`), so data changed around `Update` would reach the DataStore on the next autosave, before release. No M1 service writes around `Update`.
- **`Update` does not enforce a non-yielding mutator.** `SaveSafety.TryUpdate` runs the mutator under `pcall` and nothing stops it from yielding. The no-double-buy property (T11) holds by construction for today's mutators, which never yield, not because `Update` guarantees it.
- **Outbound remotes have no server listener.** A client can fire a server-to-client `RemoteEvent` at the server. Roblox queues events fired at a `RemoteEvent` that has no `OnServerEvent` connection, and that queue is bounded, so once it is full further events are dropped (with an engine warning). `NetGuard` never sees these events, so Outpost does not rate limit or log them.

## Accepted risks in M1

- Coins live in the profile, so an economy bug on the server can still mint Coins. M2 moves the wallet to an append-only backend ledger, planned (M2).
- A character's position is client-simulated physics, so an exploiter who teleports next to each orb before firing `Orb.Collect` passes the distance check. The cooldown, the rate limit (refill of 4 a second) and the supply of 12 orbs that respawn after 3 s keep that to about 4 pickups, 20 Coins, a second.
- Client-side HUD and orb detection can be modified freely. That only changes what the exploiter sees; the server decides everything.
- Rate limits are per server. A player hopping servers gets a fresh bucket, which is fine for a cosmetic-only game.
- If an orb pickup passes the rules but the save update is refused, the orb is already gone and nothing is paid. That fails closed on purpose.
